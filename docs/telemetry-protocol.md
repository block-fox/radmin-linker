# 在线状态与延迟协议核对

核对日期：2026-11-22。本页记录本机只读管道捕获与官方客户端二进制的验证结果，供解析器维护和回归使用。真实网络名称、成员名称与地址不写入本文或测试。

## 字段与上下文

| 消息或容器 | 字段 | 已确认语义 |
| --- | --- | --- |
| 初始状态消息 34，成员档案 `0x1322` | `E1`、`A0` | `E1` 为节点 ID；`A0` 的 bit 0 表示在线。缺失或 `FFFFFFFF` 为未知。 |
| 消息 7，`0x131F → 0x1366` | `E1`、`A0` | `CNodeOnlineChanged`，`A0 & 1` 更新在线状态。 |
| 消息 7，`0x131F → 0x1355` | `E1`、`A0` | `CNodeIgnoreChanged`，官方读取 `A0 & 2`；不能当作在线通知。 |
| 消息 28，顶层 | `E1`、`4D` | 节点 ID 与服务报告的毫秒延迟；`0` 有效，`FFFFFFFF` 为未知。 |
| 成员档案 | `21`、`26`、`3E` | 连接方向、连接类型和其他成员信息；不能据此推导在线状态或延迟。 |

这里的 `0x13xx` 表示容器 tag `13` 与末字节 ID `xx`。节点字段 `E1` 的类型为 `02`、tag 为 `01`，有效负载为 8 字节；延迟字段 `4D` 的类型为 `01`、tag 为 `03`。消息编号位于顶层标量 `01`。字段 payload 长度为大端，外层完整消息长度为小端。

`A0` 具有上下文相关的含义。将所有带 `E1+A0` 的容器递归合并，会把“取消忽略”的 `A0=0` 误当成离线。解析器只识别上表两个在线上下文，且按完整消息顺序应用。

## 官方二进制依据

核对文件为安装目录的 `RvRvpnGui.exe`，SHA-256：

```text
a9b093c68288aa8b8282feba37a254ddf45d8beabfc9f575cf8b07620825739e
```

以下地址为该文件的虚拟地址，其他版本需要重新核对：

| 位置 | 依据 |
| --- | --- |
| `0059408D`、`005940CE`、`005940E3` | 选择容器 `1366`，读取完整字段标识 `010003A0`，使用掩码 `1`。 |
| `005940E8`、`004DCB60` | 调用按位 AND 函数，随后比较结果是否为 `1`。 |
| `0059411E → 00593EF0` | 构造函数写入 vtable `010BBA20`；RTTI 指向 `CNodeOnlineChanged@rvpn`。 |
| `00593C8D`、`00593CCE`、`00593CE3` | 选择 `1355`，读取同一个 `A0`，使用掩码 `2`。 |
| `00593AC0` | 构造函数写入 vtable `010BB9C8`；RTTI 指向 `CNodeIgnoreChanged@rvpn`。 |
| `004E7409`、`004E7439` | 延迟处理函数分别读取完整字段标识 `020001E1` 和 `0100034D`。 |

在线类型的 RTTI 链为：vtable 前的指针 `010BBA1C → 010C3F34`，该结构 `+12 → 0112DB7C`，类型名位于类型描述符 `+8`。这使在线通知与忽略通知的区分能够通过字段读取及实际类型同时核对。

## 只读捕获结果与更新边界

2026-10-31 保存的捕获包含 168 个完整消息，其中消息 28 有 159 个，末尾还有 4 字节未完成数据。消息 7 同时出现 `1355/A0=0` 与 `1366/A0=1`，说明两者不能混用。

本机一次 8 秒只读订阅样本包含 1,531 个成员档案和 120 个消息 28，延迟范围为 10–5,000 ms。收到延迟的节点中，字段 `21` 分别出现 80 次 `0` 和 40 次 `1`，不能将其作为在线标志。样本也出现已有离线标志的节点随后收到延迟，因而延迟本身不能证明节点上线。

这些延迟消息在以只读权限打开 `RadminVpnGuiChannel` 后自行到达，不需要本项目发送按节点测量请求。官方界面另有名为 Ping 的连接工具；目前文档及二进制字符串核查没有确认其与消息 28 的服务测量存在命令关系，也没有确认可安全调用的“立即刷新所有节点延迟”命令。本项目首次获得每个节点的测量仍取决于服务何时推送，不承诺所有成员在固定时间内都有延迟。

初始查询以完整消息 34 的 `1320` 状态容器为结束边界。持续的延迟推送不应重置初始查询的等待时间；订阅收到完整消息后即可应用，界面读取本地最新视图无需重新查询管道。

同日本机 `nativeTelemetrySmoke` 的代表性结果如下。每次仅执行一次完整查询，随后在 4 秒内只读取本地视图；耗时包含管道打开、解码和遥测合并，不代表每个节点的首个测量都已到达。

| Minecraft | 首次完整读取 | 后续 4 秒的视图更新次数 |
| --- | --- | --- |
| 26.3 / Java 25 | 312 ms | 35 |
| 26.2 / Java 25 | 249 ms | 37 |
| 1.21.11 / Java 21 | 402 ms | 41 |

三次均正常关闭订阅线程。另以不存在的独立管道验证：订阅尚未打开时的重试不会覆盖查询的真实错误，也不会反复使已完成的视图失效。

## 缓存与并发约定

- 查询记录开始时的单调时钟，作为完整快照的时间基线；比它新的订阅状态优先，比它旧的订阅状态可由完整查询纠正。
- 完整查询先调用 `acceptSnapshot(raw, snapshotStartedAtNanos)` 保留字段存在性，再摄取结构化基线；在线档案没有延迟字段时保留有效样本，消息 28 明确返回 `FFFFFFFF` 时写入失效记录。比查询开始时间更新的订阅值仍优先。
- 每个完整消息独立应用。离线、未知状态和未知延迟保留失效记录，阻止旧快照在后续重绘时恢复旧延迟；离线状态之后排队到达的延迟不使节点上线。
- 有效延迟最多保留 60 秒。新的在线快照缺少延迟时，可使用期限内的订阅样本；反复绘制同一个基线不延长样本寿命。
- 样本失效会推进 `revision()`，供缓存视图识别变化。`clear()` 同时清理在线状态与延迟，并拒绝恢复断线之前开始的旧查询。
- `enrich(snapshot, snapshotStartedAtNanos)` 用于正常查询。兼容的单参数重载将基线视为最旧，不能覆盖有时间戳的订阅状态。
- 后端以订阅代次检查查询完成结果；已断开的旧订阅对应的查询结果不能恢复状态或写入能力。界面按稳定网络键和节点标识重新绑定选择及右键菜单对象，避免实时更新丢失高亮或继续操作旧对象。

`NetworkParsingRegression` 使用合成消息和可注入时钟验证上下文、逐帧顺序、查询竞争、查询字段缺失与显式未知的区别、零延迟、失效记录、过期、断线恢复与快照不可变性。数据来自服务通知，不使用 DNS 推断或额外 ICMP 测量。
